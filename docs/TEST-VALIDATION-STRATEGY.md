# HelioCoreOS Test and Validation Strategy

Status: Governing Solar EPC Project Addition  
Applies to: HelioCoreOS application, HelioCalc service, engineering rule profiles, cross-system reconciliation and governed workflows  
Parent accuracy framework: [Engineering Accuracy and Validation](./ENGINEERING-ACCURACY-VALIDATION.md)

## 1. Decision

HelioCoreOS must not treat `build passes` or `unit tests pass` as proof that an engineering capability is safe to become authoritative.

Testing is layered and each layer proves a different property:

```text
Static checks
→ Unit tests
→ Known-answer engineering tests
→ Boundary / invalid-configuration tests
→ Regression tests
→ Integration tests
→ Cross-system reconciliation tests
→ End-to-end governed workflow tests
→ Independent engineering validation
```

A domain becomes authoritative only when the tests required by its validation scope are present, repeatable and passing.

## 2. Test classes

### 2.1 Static application checks

Mandatory for the web application:

- TypeScript typecheck;
- lint;
- production build;
- route and import integrity;
- no committed local environment files or private credentials.

These prove software hygiene, not engineering correctness.

### 2.2 Pure calculation unit tests

Every deterministic HelioCalc function must have unit tests for:

- normal cases;
- zero and minimum values where meaningful;
- upper/lower boundaries;
- invalid values;
- unit conversion;
- sign conventions;
- rounding/tolerance behaviour;
- missing required inputs.

Identical governed inputs, engine version and rule-profile version must produce reproducible results within the declared numerical tolerance.

### 2.3 Known-answer engineering tests

Each authoritative engineering domain requires fixtures with independently established expected answers.

A fixture records at minimum:

- fixture ID;
- domain;
- source/reference method;
- governed inputs and units;
- expected result;
- accepted tolerance;
- expected findings;
- reviewer;
- validation date;
- applicable scope.

Known-answer fixtures must not be generated by the same implementation they are intended to validate.

### 2.4 Boundary and failure tests

Tests must deliberately exercise unsafe or impossible designs.

Examples:

- cold string Voc immediately below, at and above a maximum limit;
- hot Vmp below/inside/above an MPPT operating region;
- MPPT current immediately below/at/above limit;
- invalid equipment relationship;
- negative cable length;
- missing coefficient;
- inconsistent battery power/energy configuration;
- time-series energy imbalance;
- drawing/scenario equipment mismatch.

The expected result is often a machine-readable finding or controlled failure rather than a number.

### 2.5 Regression tests

Any defect that can affect an engineering result, workflow transition, document revision, BOM or drawing reconciliation must create a regression fixture before the fix is considered complete.

Historic approved-result fingerprints may also be used to detect unintended calculation changes between engine versions.

### 2.6 Integration tests

Integration tests prove boundaries between:

- Next.js server actions / API boundary;
- Supabase persistence and RLS;
- HelioCalc request/response contract;
- audit-event creation;
- calculation revision persistence;
- document/drawing revision linkage;
- approval gating.

A successful numerical response is insufficient if persistence or audit logging fails.

### 2.7 Cross-system reconciliation tests

Mandatory reconciliations include, as they become implemented:

```text
Engineering Scenario ↔ Calculation Revision
Engineering Scenario ↔ Drawing Revision
Approved Engineering Revision ↔ BOM
Approved BOM ↔ Procurement substitution controls
Design values ↔ Commissioning evidence
```

Mismatches must generate explicit findings or block transitions according to governance rules.

### 2.8 End-to-end governed workflow tests

Critical vertical slices require browser/API/database-level tests covering both success and blocked paths.

First engineering slice target:

```text
Verified equipment
→ Engineering Scenario
→ PV electrical calculation
→ Finding/margin
→ Drawing Job revision
→ Scenario/drawing reconciliation
→ Review
→ Approval
→ controlled engineering output/document revision
```

## 3. Test data rules

Test data must be deterministic and labelled.

Do not rely on live manufacturer pages, mutable weather APIs or external services for core known-answer tests.

Reference fixtures should be stored as version-controlled test data with source metadata.

Sensitive customer data must never be copied into test fixtures.

## 4. Numerical tolerance

Every floating-point comparison must declare a tolerance appropriate to the calculation domain.

Tolerance must not be used to hide material engineering error.

The test should distinguish:

- exact/discrete equality where appropriate;
- absolute numerical tolerance;
- relative numerical tolerance;
- engineering acceptance margin.

These are separate concepts.

## 5. Model validation

Predictive/modelled outputs require validation beyond deterministic unit tests.

For performance, BESS dispatch and similar models, validation may include:

- reference datasets;
- comparison to an independently accepted model/tool;
- conservation/energy-balance checks;
- sensitivity checks;
- expected directional behaviour;
- measured-vs-modelled project evidence when available.

Modelled outputs must preserve dataset identity, model version and assumptions.

## 6. Domain release gate

A HelioCalc domain may move through:

```text
DEVELOPMENT
→ BENCHMARKING
→ VALIDATED_FOR_LIMITED_SCOPE
→ VALIDATED
→ RETIRED
```

Promotion requires evidence appropriate to the scope.

`VALIDATED_FOR_LIMITED_SCOPE` must state the exact validated equipment/rule/profile/operating envelope and must not be presented as universal validation.

## 7. Continuous integration target

The intended CI gate eventually runs:

```text
Web: lint → typecheck → unit/component tests → build
HelioCalc: format/lint → unit tests → benchmark tests → regression tests
Integration: contract/database/RLS tests
Critical flow: selected end-to-end tests
```

Engineering benchmark failures must fail the release gate, not merely publish a warning.

## 8. Evidence and reporting

Every authoritative domain should expose a validation manifest containing:

- domain/version;
- validation state;
- benchmark pack version;
- number of passing fixtures;
- excluded/unsupported cases;
- known limitations;
- reviewer/approver;
- release date.

The user interface may surface this as `Calculation validation evidence`; internal implementation detail should remain out of primary workflow screens.

## 9. Initial implementation order

### TV1 — Test harness foundation
- Python test runner and deterministic fixture convention;
- frontend/application test runner;
- CI commands;
- fixture metadata schema.

### TV2 — PV electrical benchmark pack
- capacity;
- cold Voc;
- hot Vmp;
- MPPT current;
- DC/AC ratio;
- invalid/boundary cases.

### TV3 — Cross-system engineering slice
- scenario calculation persistence;
- stale state;
- drawing reconciliation;
- approval blocking;
- document revision linkage.

### TV4 — Electrical/BESS/performance expansion
Add benchmark suites only as those domains become implementation priorities.

## 10. Product decision

> **A calculation does not become engineering truth because code returned a number. It becomes authoritative only after controlled inputs, repeatable tests, independent benchmark evidence and governed release approval agree.**
